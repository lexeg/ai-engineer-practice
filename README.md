# Отчёт по проекту

## Статус аудита

Этот комплект собран из двух архивов с Qwen и OpenRouter и проверен по исходному заданию из `Проект(1).zip`. В README и `outputs/report.json` приведены только подтверждённые результаты. Неизмеренные значения оставлены как `null`, а незавершённые этапы отмечены явно.

## Финальный конфиг

- **Локальная модель:** `Qwen/Qwen2.5-1.5B-Instruct`.
- **Инференс:** vLLM 0.6.6 (версия указана в `logs/vllm.log`).
- **Точность:** FP16 (`--dtype half`).
- **Контекст:** 4096 токенов.
- **Параметры vLLM:** `--gpu-memory-utilization 0.9`, `--enforce-eager`, порт `8000`.
- **Генерация:** `temperature=0.2`, `max_tokens=800`.
- `top_p`, `top_k` и `repetition_penalty` явно не задавались — использовались значения по умолчанию.
- **Повторы при невалидном ответе:** максимум 2 попытки.
- **Лимит входа:** 1500 токенов по токенайзеру Qwen.

Команда запуска:

```bash
nohup vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 4096 \
  --gpu-memory-utilization 0.9 --enforce-eager --port 8000 > vllm.log 2>&1 &
```

В `logs/vllm.log` подтверждены загрузка весов, запуск Uvicorn и успешные ответы `GET /v1/models` со статусом `200 OK`.

## Параметры генерации

В основном сохранённом прогоне использовались `temperature=0.2`,
`max_tokens=800`. Остальные параметры явно не задавались.

Отдельно проведён предварительный эксперимент на 9 конфигурациях
с выборкой из 5 товаров на каждую конфигурацию (45 запросов).

Наилучший результат в этом эксперименте показала конфигурация:

- temperature = 0.3
- top_p = 0.9
- top_k = 20
- repetition_penalty = 1.1
- max_tokens = 350

Результат — 5/5 валидных карточек.

Это предварительный результат на небольшой выборке, а не доказательство
оптимальности конфигурации. Полная сетка из 162 конфигураций не завершена.

## Сравнение с моделью через API

Для OpenRouter найдена тестовая выборка из пяти товаров `P-0027`, `P-0032`, `P-0017`, `P-0021`, `P-0036`. Она является первыми пятью товарами файла `datasets/compare_30.jsonl`, но полный прогон на 20–30 товарах не найден.

| Метрика | Qwen, локально: те же 5 товаров | OpenRouter Particle |
|---|---:|---:|
| Валидные карточки | 5/5 (100%) | 5/5 (100%) |
| Входные токены | 5 747* | 5 573 |
| Выходные токены | 1 006 | 1 073 |
| Средняя latency запроса | не сохранена | 14,967 сек. |
| Общее время | не сохранено | 24,1 сек.** |
| Стоимость на 1000 карточек | не рассчитана | **35,17 ₽** |

\* Локальные входные токены посчитаны токенайзером Qwen; API-токены получены из `usage`. Сравнивать эти числа напрямую некорректно из-за разных токенизаторов.

\** Общее время 24,1 секунды присутствует в ранее сохранённом `report.json`, но не записано в per-card JSONL. Сумма latency пяти запросов составляет 74,836 секунды; при параллельной обработке она не равна общему времени прогона.

**Ограничение сравнения:** системный промпт в архивной версии `run_openrouter.py` отличается от локального `SYSTEM_PROMPT` в `run_batch.py`. Поэтому результаты нельзя считать строгим сравнением моделей на полностью одинаковом запросе. В комплект добавлен `compare_api.py`, который использует локальный системный промпт и параметры локального генератора.

**Ошибки API:** в одном из тестов Particle зафиксирован `429 Rate limit exceeded`. Архивная версия клиента повторяла запрос ограниченное число раз, но не реализовывала экспоненциальную задержку. В новом `compare_api.py` предусмотрены повторы для `429` и `5xx` с задержками 1, 2 и 4 секунды; `400` завершается с диагностикой, так как требует исправления параметров запроса. Ошибки `400` и `5xx` в сохранённых тестах не обнаружены.

Стоимость API рассчитана по условному тарифу задания и фактическому `usage` теста:

```text
((5573 × 20) + (1073 × 60)) / 1 000 000 / 5 × 1000 = 35,17 ₽
```

Это выше целевого ограничения 25 ₽/1000 карточек. Оценка получена на пяти карточках и не является полноценным месячным прогнозом.

Проверка подтвердила результат: 243 валидные и 57 невалидных карточек из 300. Таким образом, итоговая доля валидных карточек составляет 81,0%.

Причины нарушений (количество срабатываний правил; одна карточка могла нарушить несколько правил):

60 нарушений обнаружены в 57 невалидных карточках. Это не противоречие: одна карточка могла содержать несколько нарушений одновременно.

Результат нового запуска отличается от более раннего прогона c16, в котором было 260/300 (86,7%). Это отдельные запуски, поэтому показатели не объединяются. Для итоговой оценки производительности и качества используется новый прогон с сохранённым временем выполнения и независимой проверкой.

Артефакты нового запуска:

- `outputs/timed/benchmark_c16.jsonl` — результаты генерации;
- `logs/benchmark_c16.log` — лог выполнения и замеры времени;
- `outputs/report.json` — сводные метрики.

### Concurrency

В предыдущих экспериментах выполнены прогоны на 300 товарах с concurrency 1, 4, 16 и 32. Для них сохранились показатели валидности и количества токенов, но не сохранились elapsed time и latency.

| Concurrency | Валидных | Доля валидных | Попытка 1 | Попытка 2 | Выходные токены | Время |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 261/300 | 87,0% | 249 | 51 | 83 402 | не сохранено |
| 4 | 255/300 | 85,0% | 233 | 67 | 87 717 | не сохранено |
| 16 | 260/300 | 86,7% | 247 | 53 | 86 528 | не сохранено |
| 32 | 254/300 | 84,7% | 241 | 59 | 91 846 | не сохранено |

Дополнительно проведён новый полный benchmark с concurrency 16 и сохранением времени выполнения. Его результаты приведены отдельно в разделе «Время и стоимость локального сервера».

Сравнить throughput всех четырёх уровней concurrency по имеющимся данным нельзя. Поэтому concurrency 16 рассматривается как использованная конфигурация итогового замера, но не как экспериментально доказанный оптимум.


### Время и стоимость локального сервера

Для полного прогона 300 товаров выполнен отдельный замер с помощью `/usr/bin/time`.

| Метрика | Значение |
|---|---:|
| Количество товаров | 300 |
| Concurrency | 16 |
| Время генератора | 214,6 сек. |
| Полное время процесса | **218,24 сек.** |
| Throughput генератора | 1,40 карточки/сек. |
| Полный throughput | **1,37 карточки/сек.** |

Полное время включает выполнение Python-процесса и составляет около 3 минут 38 секунд.

Ограничение задания — не более 8 минут на 300 карточек — выполнено:

```text
218,24 сек. < 480 сек.
```

#### Стоимость локальной обработки

Для расчёта используется ставка 65 ₽/час и фактическое полное время обработки:

```text
(218,24 / 3600 × 65) / 300 × 1000 = 13,13 ₽
```

**Итоговая расчётная стоимость — 13,13 ₽ на 1000 карточек.**

Это расчёт стоимости вычислений за время обработки. Он предполагает, что ВМ оплачивается только за фактическое время работы над задачей. Если сервер арендуется постоянно, необходимо учитывать оплату простоя.

Средняя latency отдельного запроса не зафиксирована. Полное время процесса, делённое на количество карточек, характеризует производительность всего запуска, а не latency отдельного запроса.


## Длинный вход

В `dev.jsonl` есть товары с большим количеством отзывов (до 191), а в `benchmark.jsonl` — до 220 отзывов.

В `run_batch.py` реализована адаптивная предобработка длинных входных данных:

1. удаление типовых вводных фраз;
2. удаление пустых отзывов;
3. дедупликация нормализованных отзывов;
4. фильтрация части отзывов с противоречивыми формулировками;
5. отбор не более 7 уникальных отзывов;
6. подсчёт входных токенов токенайзером Qwen;
7. последовательное сокращение списка отзывов до достижения лимита 1500 токенов.

Название, категория и технические атрибуты товара сохраняются. При сокращении входа удаляются отзывы, а не характеристики товара.

### Результаты предобработки

На выборке из 40 товаров `dev.jsonl` получены следующие результаты:

| Метрика | До обработки | После обработки |
|---|---:|---:|
| Среднее количество токенов | 1962,5 | 1417,1 |
| Максимальное количество токенов | 5295 | 1460 |
| Товаров выше лимита 1500 токенов | 24 | 0 |

Средний размер входа сократился на 27,8%. Все 40 товаров после предобработки укладываются в установленный лимит.

Предобработка не гарантирует сохранение всей информации из отзывов: при необходимости часть отзывов отбрасывается. Отдельная LLM-суммаризация отзывов не используется.

## Оптимизации

Использована точность FP16 (`--dtype half`). В `vllm.log` подтверждается `torch.float16`. Сравнение с INT4 в архивах отсутствует, поэтому преимущество FP16/INT4 экспериментально не оценивалось.

## Стоимость и решение

### Сравнение стоимости

| Вариант | Стоимость на 1000 карточек | Ограничения оценки |
|---|---:|---|
| Локальная Qwen на ВМ | **13,13 ₽** | Расчёт при оплате только времени обработки |
| OpenRouter Particle | 35,17 ₽ | Предварительный тест на 5 карточках с отличавшимся системным промптом |

Локальная стоимость рассчитана по фактическому времени полного прогона 300 карточек. Стоимость OpenRouter рассчитана по фактическому `usage` пяти тестовых запросов и тарифам задания.

Сравнение пока не является окончательным: для API необходимо провести тест на 20–30 карточках с тем же системным промптом, который используется локально.

### Точка безубыточности при постоянной аренде ВМ

Для оценки рассмотрим два сценария:

1. ВМ оплачивается только за время обработки.
2. ВМ арендуется круглосуточно, независимо от нагрузки.

При постоянной аренде по ставке 65 ₽/час месячная стоимость ВМ при условных 720 часах составит:

```text
65 × 720 = 46 800 ₽/месяц
```

При предварительной стоимости API 35,17 ₽ на 1000 карточек точка безубыточности:

```text
46 800 / 35,17 × 1000 ≈ 1 330 680 карточек/месяц
```

При объёме 50 000 карточек в месяц:

| Вариант | Расчётная стоимость в месяц |
|---|---:|
| OpenRouter | 1 758,50 ₽ |
| Постоянная аренда ВМ | 46 800 ₽ |

Если ВМ оплачивается круглосуточно и используется только для этой задачи, API по предварительным тарифам экономически выгоднее при объёмах ниже примерно 1,33 млн карточек в месяц.

Если же ВМ уже арендована и используется для других задач, либо оплачивается только время обработки, локальный вариант может оказаться выгоднее.

**Предварительный вывод:** локальная модель выполнила ограничение по времени и показала расчётную стоимость ниже 25 ₽/1000 карточек при оплате только времени обработки. Окончательный выбор между локальной ВМ и API требует полноценного сравнения на одинаковых запросах и учёта режима аренды сервера.

Расчёт точки безубыточности предварительный: стоимость API пока основана на выборке из пяти карточек.


## Что осталось выполнить для полного соответствия заданию

2. Провести сравнение локальной Qwen и OpenRouter на 20–30 одинаковых товарах с идентичным системным промптом. Сохранить `usage`, время выполнения, валидность и стоимость.
3. После API-теста пересчитать стоимость и точку безубыточности с использованием результатов полноценного сравнения.
4. При необходимости выполнить замеры времени для concurrency 1, 4 и 32, чтобы сравнить их с уже измеренным concurrency 16 по throughput и latency.

Уже выполнено:

## Структура комплекта

- `run_batch.py` — локальная генерация.
- `run_batch_benchmark.py` — запуск benchmark.

- `logs/vllm.log` — лог запуска vLLM.
